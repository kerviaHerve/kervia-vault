# Unauthenticated information disclosure of internal mesh IP and version via /setup/info

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-09-22 14:24:57 UTC
**Target:** https://vault.kervia.ch
**Endpoint:** /setup/info
**Method:** GET
**CWE:** CWE-200
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Trivial

## Description

The `GET /setup/info` endpoint is publicly reachable without authentication and discloses the application's internal mesh listen address (`100.100.108.242:8321`) and software version (`v1.0.10`), aiding reconnaissance and internal-infrastructure mapping.

## Evidence

Unauthenticated request returns the disclosure:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"setup_done":true,"listen":"100.100.108.242:8321","version":"v1.0.10"}
```

The `listen` field exposes the internal mesh IP `100.100.108.242:8321`, and `version` exposes `v1.0.10`.

## Impact

An unauthenticated attacker learns the internal Tailscale/mesh IP:port where the service listens and the exact product version. This reveals internal network topology and the software version, which can be used to target version-specific vulnerabilities. The disclosed address is in the CGNAT range (100.64.0.0/10) and is not directly routable from the public internet, limiting immediate impact to reconnaissance value.

## Counterevidence

The disclosed IP is a CGNAT/Tailscale address (100.64.0.0/10) that is not directly routable from the public internet, and the version string `v1.0.10` is not itself a secret. No credentials, secrets, or restricted data were returned. This bounds the finding to low/informational reconnaissance value rather than direct unauthorized access.

## What Would Change This Severity

Confirmation that the disclosed mesh address is reachable from an attacker position (e.g. via an already-compromised node or exposed proxy) would raise the severity to medium by turning topology disclosure into a concrete attack path.

## Technical Analysis

`GET /setup/info` returns HTTP 200 with a JSON body containing `setup_done`, `listen`, and `version` fields, with no authentication required. This is the first-boot setup status endpoint that remains publicly exposed after provisioning completes (`setup_done:true`). The `listen` field reveals the internal mesh bind address `100.100.108.242:8321` (a Tailscale CGNAT address), and `version` discloses the exact build `v1.0.10`.

```http
GET /setup/info HTTP/1.1
Host: vault.kervia.ch
```

```json
{"setup_done":true,"listen":"100.100.108.242:8321","version":"v1.0.10"}
```

The endpoint serves no functional need to unauthenticated internet users after first-boot setup has completed and should not be publicly reachable.

## Proof of Concept

1. Send an unauthenticated `GET` request to `https://vault.kervia.ch/setup/info`.
2. Observe the HTTP 200 response body discloses the internal listen address and version.

```scdoc
curl -s https://vault.kervia.ch/setup/info
# {"setup_done":true,"listen":"100.100.108.242:8321","version":"v1.0.10"}
```

## Remediation

Restrict the `/setup/info` endpoint to only respond before first-boot setup completes, or require authentication once `setup_done` is true. Remove the internal `listen` address from the public response (or omit it entirely once provisioned). Avoid exposing exact software versions publicly, or gate them behind authenticated admin access.

## Assumptions

Assumes the endpoint remains reachable by unauthenticated internet users; confirmed via direct request.
